# Create a verification skill

Manual skill. Run it when the user asks for it, or when a recipe the user invoked composes it by name. If it loads without either, say so and stop instead of generating anything.

Every serious project needs a scripted way to drive the real app and prove behavior: launch it, exercise a feature the way a user would, and capture evidence. This skill generates that as a project-local skill (`.agents/skills/verify-<app>/`) tailored to the repo, with a driver CLI that agents run instead of writing throwaway scripts. You write the generator's output for the next agent, not for a human: it will be read cold, mid-task, by an agent that has never seen the app.

## 1. Interview the repo, not the user

Answer these from the codebase and only ask the user what you cannot observe:

- **Stack:** languages, frameworks and versions from the manifests and lockfiles; the test runner, the type checker, the linter and the command CI runs. They decide the CLI's language, the harness it reuses and the smoke test's runner.
- **Surface:** what does a user actually touch? A web UI, a CLI/TUI, a desktop app, an API, a mobile app, a library? A repo can have several; pick the primary one and note the rest.
- **Run:** how does the app start locally? Prefer the repo's own documented dev command (package scripts, Makefile, README quickstart). Note ports, env vars, seed data, auth.
- **Drive:** how can an agent interact with it programmatically? Existing harnesses first — Playwright/Cypress specs, expect scripts, PTY helpers, curl-able endpoints, a debug port. Only then pick a generic recipe: browser/CDP for web and Electron, a tmux/PTY harness for CLI/TUI, plain HTTP for services. Reuse the repo's driver library, locators and documented commands, called from the CLI so each drive acts on one live session instead of one fresh test run per feature. A second test framework standing beside the existing one is a maintenance burden the repo did not ask for.
- **Observe:** what evidence can be captured? Videos, screenshots, accessibility snapshots, terminal transcripts, response bodies, logs, exit codes, DB state.
- **Isolate:** derive ports, browser profile and data dir from the checkout path, so two checkouts run side by side. Keep every directory where the app or its browser creates a Unix socket (its temp dir, the browser profile) short and hashed, under `/tmp`: operating systems cap socket paths near 100 bytes. If the app cannot run twice, say so in the generated skill: refusing to double-drive a shared instance beats corrupting the user's session.

Then show the user a short inventory: the stack; each surface with its user-facing features; the driver you propose for each surface (the repo's harness, or a generic recipe and what it needs); and the 3-5 features you will map first (step 3). Ask what is missing or wrong, such as a service, tool or internal library the repo doesn't declare, a feature, or a better driver. Add what they name before generating.

If the checkout doesn't build or start as-is, fix that first (or report it precisely) before generating; a skill written against a broken base teaches wrong steps. When an irrelevant missing asset blocks startup (a static dir the API never serves, a sample config), the generated skill may create it, clearly marked as verification scaffolding, and remove it in cleanup.

## 2. Generate the skill

Write `.agents/skills/verify-<app>/SKILL.md` with YAML frontmatter (`name: verify-<app>` and a `description` that names the app, the surface, and when to reach for it — without frontmatter the skill never registers) and these sections, each grounded in what the interview actually found (no placeholders left):

- **CLI:** one executable driver command in the skill directory, in the repo's main language, that every other section calls. The repo's own manifests stay as they are; a compiled driver is its own package in the skill directory. Its subcommands are doctor, launch, the drive primitives, the debug commands and cleanup. A drive primitive is one kind of user action (open, click, fill, press a key, type a command, send a request) on the live session — for a short-lived CLI, a fresh isolated one — and returns what it observed; feature recipes compose primitives. Every subcommand has `--help`, which prints usage with a real example from this repo; every other invocation prints JSON on stdout and turns each error into the command to run next; destructive ones take `--dry-run`. The skill body shows each invocation, and every helper script is executable. [poteto/verification-skill-example](https://github.com/poteto/verification-skill-example) shows a full command surface; it has no licence, so read it for ideas and write the code yourself.
- **Launch:** the exact command that starts the app for verification, and how to tell it's ready (a log line, a prompt). Launch must reach a usable state from an empty data dir, including any migrations and seed data. Ready means usable, not just that a process answers. A database health check can pass while its init scripts are still running. Include teardown. For a short-lived CLI or TUI there is no server to keep alive: launch means build the binary (or install deps) once, then start each drive as its own isolated process: in a PTY or tmux session when the app needs a terminal, otherwise with stdin, stdout and stderr captured separately.
- **Doctor:** one read-only check that answers "is this instance worth driving?" — process up, the running build matching the checkout's source, every resource it needs (port, display, socket, lock file) held by this run, auth valid. It names the PID and command of anything else holding a resource, and refuses an instance another checkout started. A stale build is not evidence: every drive primitive repeats the build check and, on a mismatch, refuses and names cleanup and launch as the next commands instead of rebuilding, which loses the session state. An agent runs doctor first whenever anything looks off.
- **Drive:** the harness recipe with real selectors/commands from this repo, not examples. Prefer stable handles (ARIA labels, data attributes, prompt strings, route paths) over coordinates and tab order.
- **Debug:** commands that read the live session in its current state, leaving it unchanged, from what the surface exposes: a screenshot, the accessibility tree, console and network for a UI; the terminal transcript and exit code for a CLI or TUI; the request, response and stored state for a service. Each writes its artifact to the evidence location and prints the path.
- **Evidence:** what to capture for a proof and where it goes. State the proof standards: exercise the real user path, not internal setters or test-only endpoints; capture the action and the resulting state, not just the final screen; verify side effects (files written, rows inserted, messages sent) alongside what's visible; mocks only where a production boundary already isolates the external system. When the safe path is a dry-run or test mode, verify what it actually skips by observing (files, network, git refs) rather than trusting its name: some dry-runs still touch the network or open a browser. A change's proof covers every entry point, mode and flag variant it affects, through its success, cancel, error, empty and persistence paths. Each step waits for an observable end state, never a fixed sleep; `eval` only reads state after the user path ran. For a UI, screenshots before the trigger and of the end state are the default proof; add a video when the states in between matter. A report gives each step's command, exit code, expected and observed result and evidence path; a step reported without them counts as not run.
- **Cleanup:** how to tear down instances the run created. Never kill by process name; kill what you started. Cleanup removes instances and scratch state, never the evidence: proof artifacts survive the teardown, in a location the skill names.
- **Smoke test:** one test in the skill directory, run by the repo's own test runner: launch, doctor, one drive on seed data, cleanup. The skill body shows the exact command with the test's path, because runners often skip hidden directories such as `.agents/`; the runner's output lists it as run. `/maintain-verification-skill` keeps it green.

## 3. Seed the feature map

Create `.agents/skills/verify-<app>/features/README.md` plus one file per user-facing feature, starting with the 3-5 that users reach most on the primary surface (from routes, commands, menus, or docs). Follow the shape in `references/feature-map-example/`, read as `skill://create-verification-skill/references/feature-map-example/README.md` in OMP or through `skill_view` in Hermes: a README index that gives each feature the words users call it, and one file per feature. Each file answers, from the user's point of view: what the feature is, how to reach it, how to drive it with the harness, and what observable end state proves it works. The four H2s are `Sub-features`, `How to get to it (user POV)`, `Driving it with <harness>`, and `Gotchas`, verbatim.

`Sub-features` lists every variant the user docs and help text promise (each documented shortcut, option, mode or command form). The recipe drives each one, or the README's `Not yet mapped` list names it; that list also names each surface and feature left out. One line may name several, while a group such as "more options" names none. When this machine cannot run an entry (another OS, a desktop session, several displays, a device, an external service), the entry proposes a way to recreate it that you checked exists: a container image, a VM, an emulator, a nested display server, or a local stand-in for the service. Install nothing: the user picks.

If the seed data lacks a precondition that a journey needs, the journey reports a failure and the reason goes in that feature's `Gotchas`. Never weaken the journey to make it pass. The map is the repo's maintained verification source; a proof that drives one convenient entry point is incomplete when the map lists others.

## 4. Prove the generated skill before handing it over

Run its own instructions end to end once: launch, doctor, drive one mapped feature with full evidence, clean up. After cleanup, confirm the evidence still exists at the named location — a cleanup that eats the proof fails this step. Then run every other recipe once, verbatim from its preconditions, and the smoke test with the command the skill shows. Fix what fails, and run the generated cleanup after every failed iteration too, so broken attempts don't strand processes and ports. Report a product bug to the user rather than editing around it. A recipe blocked by a prerequisite only the user can install keeps its failing command in `Gotchas` and is listed as unproven, with a recreation proposal as in step 3. This step is done when every recipe has run (passed, failed on a product bug you reported, or unproven with its failing command) and the runner's output lists the smoke test as passed. Hand off in the generated skill's report format, ending with the `Not yet mapped` entries and asking which to map next. A generated skill that was never executed is a draft, not a deliverable. If you proved it in a stand-in for the real target (a container in place of a fresh VM, a local stack in place of a remote one), list every setup step the stand-in did that the target will not. Those steps stay unverified until a run on the real target covers them.

## 5. Offer the maintenance loop

Point the user at `/maintain-verification-skill` for keeping the map honest as the app changes. Suggest a cadence only if they ask.

## 6. Register it on the runtime that will use it

A generated skill nobody loads is a file. OMP discovers project-local skills under the repo's `.agents/skills/`; confirm it from the repo root with `omp read skill://verify-<app>`, which prints the generated SKILL.md when discovery works. Hermes is the secondary runtime here, and it only discovers a project's `.agents/skills/` after the human runs `hermes skills trust` for that directory. Never trust it for them and never edit their global Hermes configuration: either ask them to run the trust command, or hand the next agent the explicit-file route (`skill_view` on `.agents/skills/verify-<app>/SKILL.md`). Say in the hand-off which of the two applies, so nobody assumes discovery that isn't there.
