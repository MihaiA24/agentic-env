# Create a verification skill

Manual skill. Run it when the user asks for it, or when a recipe the user invoked composes it by name. If it loads without either, say so and stop instead of generating anything.

Every serious project needs a scripted way to drive the real app and prove behavior: launch it, exercise a feature the way a user would, and capture evidence. This skill generates that as a project-local skill (`.agents/skills/verify-<app>/`) tailored to the repo, with a driver CLI that agents run instead of writing throwaway scripts. You write the generator's output for the next agent, not for a human: it will be read cold, mid-task, by an agent that has never seen the app.

## 1. Interview the repo, not the user

Answer these from the codebase and only ask the user what you cannot observe:

- **Stack:** languages, frameworks and their versions from the manifests and lockfiles; the test runner, type checker and linter; the command CI runs. These decide the CLI's language, the harness to reuse and the runner for the smoke test.
- **Surface:** what does a user actually touch? A web UI, a CLI/TUI, a desktop app, an API, a mobile app, a library? A repo can have several; pick the primary one and note the rest.
- **Run:** how does the app start locally? Prefer the repo's own documented dev command (package scripts, Makefile, README quickstart). Note ports, env vars, seed data, auth.
- **Drive:** how can an agent interact with it programmatically? Existing harnesses first — Playwright/Cypress specs, expect scripts, PTY helpers, curl-able endpoints, a debug port. Only then pick a generic recipe: browser/CDP for web and Electron, a tmux/PTY harness for CLI/TUI, plain HTTP for services. Reuse the repo's harness: its driver library, locators and documented commands. When its runner can only run whole test files, the driver CLI calls that same library directly, so each drive primitive acts on one live session instead of one fresh run per feature. A second test framework standing beside the existing one is a maintenance burden the repo did not ask for.
- **Observe:** what evidence can be captured? Videos, screenshots, accessibility snapshots, terminal transcripts, response bodies, logs, exit codes, DB state.
- **Isolate:** derive ports, browser profile and data dir from the checkout path, so two checkouts run side by side. Ports the app takes from the OS (port 0) for its own internal use are already unique; leave them to the OS. Keep Unix socket paths short, under a hashed directory in `/tmp` rather than deep in the checkout: Linux caps them at 108 bytes and macOS at 104, and Chromium fails with `Socket path too long` past that. If the app cannot run twice, say so in the generated skill: refusing to double-drive a shared instance beats corrupting the user's session.

Then show the user, in a few lines, the stack and surface you found, and ask whether any part is missing, such as a service, tool or internal library the repo doesn't declare. Add what they name before generating.

If the checkout doesn't build or start as-is, fix that first (or report it precisely) before generating; a skill written against a broken base teaches wrong steps. When an irrelevant missing asset blocks startup (a static dir the API never serves, a sample config), the generated skill may create it, clearly marked as verification scaffolding, and remove it in cleanup.

## 2. Generate the skill

Write `.agents/skills/verify-<app>/SKILL.md` with YAML frontmatter (`name: verify-<app>` and a `description` that names the app, the surface, and when to reach for it — without frontmatter the skill never registers) and these sections, each grounded in what the interview actually found (no placeholders left):

- **CLI:** one driver command in the skill directory, in the repo's main language, that every other section calls. In a compiled language, make the driver its own package in the skill directory with a small launcher script that builds it, so the repo's root manifest stays as it was. Its subcommands are doctor, launch, the drive primitives, each debug command and cleanup. A drive primitive is one kind of user action on the surface (open, click, fill, press a key, type a command, send a request): it acts on the live session (for a short-lived CLI, a fresh isolated one) and returns what it observed. Feature recipes compose primitives, so a new journey needs only a new recipe. Every subcommand has `--help` with a real example from this repo, prints JSON on stdout, and turns each error into the command to run instead. Destructive subcommands take `--dry-run`. The CLI and any helper are executable, and the skill body shows each invocation. For a full command surface, compare [poteto/verification-skill-example](https://github.com/poteto/verification-skill-example). It has no licence, so read it for ideas and write the code yourself.
- **Launch:** the exact command that starts the app for verification, and how to tell it's ready (a log line, a prompt). Launch must reach a usable state from an empty data dir, including any migrations and seed data. Ready means usable, not just that a process answers. A database health check can pass while its init scripts are still running. Include teardown. For a short-lived CLI or TUI there is no server to keep alive: launch means build the binary (or install deps) once, then start each drive in its own isolated PTY or tmux session.
- **Doctor:** one read-only check that answers "is this instance worth driving?" — process up, right version/build, every resource it needs (port, display, socket, lock file) held by this run, auth valid. When anything else holds one of them, doctor and launch name the holder's PID and command, and launch takes a free one from its derived block or refuses. Doctor reports whether the running build matches the checkout's current source, and it refuses an instance another checkout started. A stale build is not evidence: every drive primitive runs the same build check before it acts, and on a mismatch it refuses and names cleanup and launch as the next commands. It never rebuilds on its own, because a rebuild restarts the app and loses the session state the recipe built. An agent runs doctor first whenever anything looks off.
- **Drive:** the harness recipe with real selectors/commands from this repo, not examples. Prefer stable handles (ARIA labels, data attributes, prompt strings, route paths) over coordinates and tab order.
- **Debug:** commands that show the agent what happened, from what the surface exposes: for a UI, a screenshot, the accessibility tree, console and network; for a CLI or TUI, the terminal transcript (from a PTY, or from the repo's own input harness when the app needs no TTY) and the exit code; for a service, the request, the response and the stored state. Debug reads the live session the drives act on, in its current state, and leaves it unchanged. Each command writes its artifact to the evidence location and prints the path.
- **Evidence:** what to capture for a proof and where it goes. State the proof standards: exercise the real user path, not internal setters or test-only endpoints; capture the action and the resulting state, not just the final screen; verify side effects (files written, rows inserted, messages sent) alongside what's visible; mocks only where a production boundary already isolates the external system. When the safe path is a dry-run or test mode, verify what it actually skips by observing (files, network, git refs) rather than trusting its name: some dry-runs still touch the network or open a browser. A change's proof covers every entry point, mode and enabled flag variant the change affects, through the success, cancel, error, empty and persistence paths. Each step waits for an observable end state; a fixed sleep proves nothing. `eval` only reads state after the user path ran. For UI, screenshots are the default proof: one before the trigger and one of the stable end state, with snapshots as support. Record a video when the proof depends on the states in between, such as loading, animation or the order of updates.
- **Report:** the format an agent uses to report a verification made with this skill. For each step: the command, its exit code, the expected result, the observed result and the evidence path. Then every step that did not run, with the reason. Each failure is marked as a product bug, a verifier problem or an environment problem. A step reported without its command and observed result counts as not run.
- **Cleanup:** how to tear down instances the run created. Never kill by process name; kill what you started. Cleanup removes instances and scratch state, never the evidence: proof artifacts survive the teardown, in a location the skill names.
- **Smoke test:** one test in the skill directory, run by the repo's own test runner: the CLI's launch, then doctor, then one drive on seed data, then cleanup. The skill body shows the exact command, with the test's path: runners often skip hidden directories such as `.agents/`, so the runner's output must list the test as run. It proves the CLI still works, and `/maintain-verification-skill` keeps it green.

## 3. Seed the feature map

Create `.agents/skills/verify-<app>/features/README.md` plus one file per user-facing feature, starting with the 3-5 that users reach most on the primary surface (from routes, commands, menus, or docs). The README names the surfaces left unmapped, so the next pass sees the gap. Within a mapped feature, `Sub-features` lists every variant the user docs and help text promise for it (each documented shortcut, option, mode or command form), and the recipe drives each one. The README's unmapped list names each variant the recipe leaves out. One line may name several, as long as each one is named; a group such as "more options" names none. When an entry is unmapped because this machine cannot run it (another OS, a desktop session, several displays, a browser or device, an external service or cloud API), the entry also proposes a way to recreate that environment: a container image or Compose service, a VM, an emulator, a nested display server, or a local stand-in for the service, such as a mail catcher or a cloud API emulator. Propose only tools you checked exist (an official image, the project's docs, the repo's own CI), mark any you could not check as unchecked, and install nothing: the user picks. Follow the shape in `references/feature-map-example/`, read as `skill://create-verification-skill/references/feature-map-example/README.md` in OMP or through `skill_view` in Hermes, with a README index and one file per feature. Each file answers, from the user's point of view: what the feature is, how to reach it, how to drive it with the harness, and what observable end state proves it works. The four H2s are `Sub-features`, `How to get to it (user POV)`, `Driving it with <harness>`, and `Gotchas`, written verbatim in English whatever language the repo's docs use, so every map has the same shape. Every driving step runs as written: the exact command, scoped to exactly one handle, and the result it expects. The README index gives each feature the words users call it, such as "left sidebar" for `left-rail.md`, so a request in the user's words resolves to one file. If the seed data lacks a precondition that a journey needs, the journey reports a failure and the reason goes in that feature's `Gotchas`. Never weaken the journey to make it pass. The map is the repo's maintained verification source; a proof that drives one convenient entry point is incomplete when the map lists others.

## 4. Prove the generated skill before handing it over

Run its own instructions end to end once: launch, doctor, drive one mapped feature with full evidence, clean up. After cleanup, confirm the evidence still exists at the named location — a cleanup that eats the proof fails this step. Then run every other recipe in the map once, verbatim from its preconditions: a recipe nobody ran is a draft too. When a step fails, fix the recipe or the harness. Report a product bug to the user rather than editing around it. When the environment lacks a prerequisite only the user can install, keep the recipe, put the failing command in its `Gotchas`, and list the recipe as unproven in the hand-off with a proposed way to recreate the prerequisite, checked as in step 3. Then run the smoke test with the command the skill shows. This step is done when every recipe has run (passed, or listed as unproven with its failing command) and the runner's output lists the smoke test as run and passed. Write the hand-off in the generated skill's Report format, followed by every recreation proposal from the map and the unproven recipes, so the user can pick which environments to add. Fix what fails, and run the generated cleanup after every failed iteration too, so broken attempts don't strand processes and ports. A generated skill that was never executed is a draft, not a deliverable. If you proved it in a stand-in for the real target (a container in place of a fresh VM, a local stack in place of a remote one), list every setup step the stand-in did that the target will not. Those steps stay unverified until a run on the real target covers them.

## 5. Offer the maintenance loop

Point the user at `/maintain-verification-skill` for keeping the map honest as the app changes. Suggest a cadence only if they ask.

## 6. Register it on the runtime that will use it

A generated skill nobody loads is a file. OMP discovers project-local skills under the repo's `.agents/skills/`; confirm it from the repo root with `omp read skill://verify-<app>`, which prints the generated SKILL.md when discovery works and `Unknown skill` when it does not. Hermes is the secondary runtime here, and it only discovers a project's `.agents/skills/` after the human runs `hermes skills trust` for that directory. Never trust it for them and never edit their global Hermes configuration: either ask them to run the trust command, or hand the next agent the explicit-file route (`skill_view` on `.agents/skills/verify-<app>/SKILL.md`). Say in the hand-off which of the two applies, so nobody assumes discovery that isn't there.
